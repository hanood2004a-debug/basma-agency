## 4. New APIs

- `POST /api/crm-send-email` — the only server route in this phase. Authenticates the caller's own Supabase session (forwards their access token + the public anon key), validates input, checks suppression, calls Resend, records the outcome, and best-effort updates `crm_outreach`/`crm_activities`/schedules a follow-up. Never uses the service-role key — every write is still governed by `crm_can_write()` RLS exactly as if the browser had called supabase-js directly.

## 5. New functions/triggers

- `crm_schedule_followup(company_id, message_id, days, channel)` — atomically supersedes the company's previous auto-generated pending follow-up, updates `crm_outreach.next_follow_up_date`, and inserts one new linked task. The single place that creates follow-ups, called from every channel (including message-less "Schedule Follow-up" quick actions).
- `crm_set_response_status(company_id, status)` — atomically sets the unified response tracker and, when set to `replied`, cancels the company's pending auto-follow-up in the same transaction.
- `crm_campaign_metrics(campaign_id)` — derived, never stored, campaign metrics (recipients/sent/failed/waiting_reply/replied/interested/meetings/proposals/won).
- `crm_outreach_dashboard_snapshot()` — `CREATE OR REPLACE`, extended. Every pre-existing key is preserved byte-for-byte; everything new lives under one new `automation` key.
- `crm_campaigns_set_updated_at` — reuses the existing `crm_set_updated_at()` trigger function.

## 6. Email architecture

Browser → `/api/crm-send-email` (with the user's own Supabase access token) → server verifies the token via Supabase Auth → server checks contact suppression → server calls Resend directly (`RESEND_API_KEY`, server-only) → server writes the outcome to `crm_outreach_messages` using the anon key + the user's token (so RLS applies) → on success only: best-effort update `crm_outreach.email_status`, log `crm_activities`, optionally call `crm_schedule_followup`. A Resend failure records a `status='failed'` row and returns an error — it never touches `crm_outreach`/`crm_companies`/`crm_leads`.

## 7. WhatsApp architecture

Assisted only — no official WhatsApp API is configured, so nothing here claims to "send" automatically. The composer renders the template, opens `https://wa.me/<number>?text=<encoded>` in a new tab, and only writes a `crm_outreach_messages` row (`status='sent'`) after the user explicitly clicks "تأكيد الإرسال" (Confirm Sent) — never merely because the link was opened.

## 8. LinkedIn architecture

Same assisted pattern as WhatsApp: Copy Message + Open Profile, then an explicit "تأكيد الإرسال" step before anything is logged. No automatic send is implemented or implied anywhere in the UI copy.

## 9. Campaign architecture

`crm_campaigns` is a lightweight shell (name/channel/template/status) with `crm_campaign_members` as the join table to companies (and optionally a resolved contact). Metrics are **never** stored on the campaign row — `crm_campaign_metrics()` computes them live by joining `crm_campaign_members` against `crm_outreach_messages`/`crm_outreach`/`crm_meetings`/`crm_proposals`/`crm_leads`, so they can never drift out of sync with reality.

## 10. Anti-duplicate safeguards

- **Cooldown check**: before composing or bulk-queuing, the same company+channel+template combination sent within the last 24 hours (`COOLDOWN_HOURS`, one constant in `crm-composer.js`) triggers a visible warning that requires an explicit checkbox to override — it never blocks silently and never sends silently.
- **Follow-up dedup**: `is_auto_followup` is the single, unambiguous marker `crm_schedule_followup()` uses to supersede a company's own previous pending auto-follow-up (covers both message-triggered and message-less "Schedule Follow-up" quick actions) — manually created tasks are never touched.
- **Bulk send**: the review queue in `outreach.html` excludes companies with no valid recipient, an invalid email, or a suppressed contact from the sendable count by default, and only includes cooldown-flagged rows if the user explicitly opts in via a separate checkbox.
- **Suppression**: `crm-send-email.js` hard-blocks (400) sending to a contact flagged `email_suppressed`, before ever calling Resend.

## 11. Follow-up automation logic

Default 5 days, selectable 1/2/3/5/7/14/custom, everywhere a follow-up can be scheduled (Email composer, WhatsApp/LinkedIn confirm-sent, phone call outcome, and the standalone "Schedule Follow-up" quick action). Every path funnels through the one `crm_schedule_followup()` function, which is the only code that writes `crm_outreach.next_follow_up_date` for this purpose — so it is automatically visible in the Outreach Calendar, Company 360, and Outreach Hub (all of which already read that column), and the linked `crm_tasks` row participates in Tasks/Notifications as those already do.

## 12. Security review

- `RESEND_API_KEY` is read in exactly one file (`api/crm-send-email.js`) and never sent to the browser.
- `SUPABASE_SERVICE_ROLE_KEY` is **not used anywhere** in this phase — the new endpoint forwards the calling user's own access token, so Postgres RLS (`crm_can_read()`/`crm_can_write()`) is the sole authority on every read/write, with zero duplicated permission logic in JavaScript.
- All new tables have RLS enabled with the project's standard convention: `select` via `crm_can_read()`, `insert`/`update` via `crm_can_write()`, `delete` restricted to `is_admin()`.
- No secrets appear in any HTML/JS file added or modified in this phase (verified by inspection — the only new env-var reads are inside `api/crm-send-email.js`).

## 15. Environment variables required

- `RESEND_API_KEY` — **new**, server-only, required for `/api/crm-send-email` to function (the endpoint returns 503 if missing).
- `SUPABASE_URL`, `SUPABASE_ANON_KEY` — already in use elsewhere in the project; the new endpoint reuses them (no service-role key needed).
- `CRM_OUTREACH_FROM_EMAIL` (optional) — falls back to `NOTIFY_FROM_EMAIL`, then to a hardcoded default `Basma CRM <notifications@basmadigital.com>`.

## 16. Known limitations

- Cooldown window (24h) is a hardcoded constant in `crm-composer.js`, not an admin-configurable setting.
- Suppression is minimal scaffolding (a boolean + reason on `crm_contacts`, enforced server-side) — there is no public unsubscribe link/page; that would be a separate, larger, compliance-grade feature.
- WhatsApp/LinkedIn "send" is, by design, assisted (open link / copy text + explicit confirm) — there is no bulk-send for these channels, since no official API is configured; the Bulk Outreach review queue in Outreach Hub is Email-only.
- Bulk email batching is a fixed client-side constant (3 per batch, 1.5s between batches) — not configurable via UI.
- Campaign member "candidate search" in `outreach-campaigns.html` is capped at 30 results per search and does not paginate.
- The `crm_campaign_members` embed query in `outreach-campaigns.html` (see section 13) has not been verified against a live Supabase/PostgREST instance.
- Metrics on the Campaigns list page require one `crm_campaign_metrics` RPC call per visible campaign (not batched) — fine at expected campaign-list sizes, would need batching if campaign counts grow very large.
